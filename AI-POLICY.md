# Arcana Land AI Policy

Arcana Land's goal of providing free and open-source resources, standards and tooling for all things tarot is an ambitious one. Creating detailed specifications, shared libraries, command-line tools, GUI applications, curated sets of assets and data plus packaging and distribution of all of the above is a large amount of work for a single person working on it unpaid as a hobby.

Because of this, LLMs are used in this project, but in a very narrow scope. Essentially, the goal is that any piece of art presented to the user was created by a human and any text presented to the user was written by a human.

Text that is primarily meant for human consumption, such as (but not limited to) display strings, alt text, esoterica and documentation must be written by a human. Text designed to be read by both machines and humans, like code, configuration files and specification prose can be generated by an LLM, but it needs to be understood and vetted by the contributor.

Golden rule: an end-user should never see a piece of text or art created by a machine.

## 1. Generated Art Strictly Prohibited

Every piece of art in every Arcana Land repo is created by a human. This includes app logos, website assets, banners and any other art related to Arcana Land projects.

This rule also extends to any deck that is included in its set of reference decks.

## 2. Generated Text Intended for Humans Prohibited

All text that is mainly meant for humans to read (including this document!) must be written by a human.

> The one open exception that I hope to close is that the reference Rider-Waite-Smith deck's [alt-text](https://github.com/arcanaland/reference-decks/blob/main/rider-waite-smith/names/en.toml) was written by an LLM and I would really like to replace it. I am currently writing my own by hand that I plan to release at some point under CC-BY-4.0, but it is slow-going.
>
> If anyone is willing to write English alt text (or in any language) for the traditional 78 cards and release it under a CC license please contact me or feel free to open a PR!

## 3. Generated Code and Prose Intended Mostly for Machines Allowed

### 3.1 Code

Code written by LLMs is okay. Merging unreviewed, untested slop is not. Understand the code that is being written and the problem being solved.

Try to keep generated code that is in the process of being reviewed in a branch prefixed with `slop/` to signal that it is not fully baked.

### 3.2 Specifications

Specifications have always been in kind of a gray area. They typically read as if a robot wrote them since they are primarily written to describe a problem in a precise and formal way, so it being robotic is by design. There is a reason some specs are derided for being heavy with the jargon and "specese" and seemingly barely intelligible despite having been penned by mortal hands.

So LLM spec prose is okay, but be mindful of the human reader and keep it concise. And please never use the phrases "load-bearing" or "footgun."
